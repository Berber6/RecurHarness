**任务**：`ariga__atlas.6d81150`
**日期**：2026-10-25

| | baseline | v1.4.6 | **v1.5.1** |
|---|---|---|---|
| **分数** | 72 | 89 | **87** |
| **成本** | $36.5 | $64.9 | $39.0 |
| **时长** | 2.6h | ~4.2h | 8.4h |

| 总通过 | 1180/1732 (68%) | 1548/1732 (89%) | **1513/1732 (87%)** |

**结论**：v1.5.1 补上了 v1.4.6 留下的缺口——验收断言此前从未被程序验证过。本版把验证

缺陷，误杀从 149 条降到 3 条。分数 87，略低于 v1.4.6 的 89，代价是断言分配不均。

# 一、优化动机

## 1.1 上一版留下了什么

v1.4.6 用 checks 验收机制拿到 89 分：探测阶段把观察到的行为写成可执行断言，规划阶段
分派到模块，实现阶段跑通才算完成。报告里自己点名了一个短板：

> 提示词要求只收录验证跑通过的检查，但产物里无法确认 agent 真的逐条重跑验证过，
> 更可能是根据已有结果反推。反推就可能出笔误，比如 setup 建的目录和 command 里写的
> 路径对不上。

也就是说，**那 56 条驱动了整个实现流程的断言，没有任何一条被程序验证过。** 模型说它
验证了，就当成验证了。

## 1.2 短板有多大

本版把验证做成程序实跑之后，这个短板第一次能被量化。探测写出的 198 条断言里，
实跑通过 137 条，**61 条是错的**——路径写错、期望值写错、或者根本跑不起来。

```
探测声称: 198 条
程序实跑: 137 条通过, 57 条淘汰, 4 条降级为弱断言
```

三分之一的断言不成立。在上一版里，这些错误断言会被原样分派到模块，让实现去追逐一个
不存在的行为——`migrate_apply` 分到 12 条检查、修满 150 步仍未收敛，很可能就是因为
其中有假目标。

问题还不止于此：验证脚本自己也会误判。同一批断言，在两种实现下实跑的有效数不同：

| 验证实现 | 有效 | 淘汰 |
|---|---|---|
| 早期版本 | 118 | 149 |
| 修正路径处理后 | 254 | 3 |

差异全部来自验证脚本的缺陷——setup 建文件的位置和命令运行的位置对不上。
**断言是被验证环境判死的，不是被真实行为判死的。**

> 验收机制的第一环是"这些断言是真的"，而这一环此前完全依赖模型自述。

这就是这一版要解决的动机：**把断言的验证从模型自述变成程序实跑，并且让验证本身可靠。**

# 二、v1.5.1 版本改动

本版只改探测阶段的提示词，外加修复验证环节的一个实现缺陷。

## 2.1 改动一：探测提示词

探测阶段原本的提示词给了一个参考值：

```
Say 10-20 checks in probe_checks.json is a good target
```

这句话在实测中被当成了上限。同一份提示词跑六次，checks 只作出 25–49 条，模型在
"25 条已经超标，要不要删几条"上反复纠结然后收工。

本版把这句话换成"每条子命令、每种输入族都要有断言，没有上限"，同时补了两类此前
完全没覆盖的探测对象：

- **内嵌表达式语言**：模板串、查询表达式、格式串，其函数集常由工具自己扩展，
  `--help` 里看不到。要求把完整函数清单当交付物，逐个跑一遍。
- **隐藏命令**：开源核心版常见 `--help` 不显示、调用会返回"不受支持"的子命令，
  这类拒绝文案是会被评测的。要求对每个命令组穷举候选子命令名，逐字记录三种结果：
  能用、存在但被禁用、根本不存在。

效果：checks 从 56 条涨到 198 条，探到了 `schema test`、`migrate down` 等 gated
命令和 13 个模板函数。三处只动了探测阶段，其余三个阶段未改。

## 2.2 改动二：验证环节的误杀

探测收尾时由程序实跑每条断言，跑不通的丢弃。这一步没有模型参与，但实现上有三个缺陷，
把好断言也误杀了：

| 缺陷 | 症状 | 修法 |
|---|---|---|
| setup 里的 `cd /workspace &&` | 文件建在 workspace，命令在临时目录跑，路径对不上 | 剥离该前缀 |
| setup 把夹具写在 `/workspace/x`，命令写相对路径 `x` | 同上 | setup 后把 workspace 路径镜像进临时目录 |
| 参考二进制权限是 `---x--x--x` | 任何读它的 setup 报 PermissionError | 运行前补读权限 |

修复前后对比（同一批断言，在容器内实跑）：

| 验证实现 | 有效 | 淘汰 |
|---|---|---|
| 修复前 | 118 | 149 |
| 修复后 | **254** | **3** |

## 2.3 实际验证

| 环节 | 数量 |
|---|---|
| 探测 findings | 314 |
| 探测写出的断言 | 198 |
| 程序实跑通过 | 137（另 4 条降级为弱断言，57 条淘汰） |
| 分派到模块 | 137/137 |
| 模块数 | 10 |

一条真实的检查长这样：

```json
{ "command": "./executable schema test",
  "setup": "mkdir -p \"$HOME/.atlas\" && : > \"$HOME/.atlas/local-community.json\"",
  "expect": { "exit_code": 1,
              "stderr_contains": ["Abort: 'atlas schema test' is not supported by the community version."] } }
```

它断言的正是那 35 个隐藏命令测试的行为。

# 三、结果

## 3.1 功能块对比

七个大类按同一套口径统计，各版本之间可比。

| 块 | 测试数 | baseline | v1.4.6 | **v1.5.1** |
|---|---|---|---|---|
| basic/cli | 719 | 94.8% | **99.2%** | 98.7% |
| migrate | 451 | 44.7% | **86.0%** | 85.1% |
| **schema** | 278 | 71.4% | **94.9%** | **86.0%** |
| cmdlog | 86 | 5.3% | **54.7%** | 51.2% |
| config/env | 77 | 68.6% | **81.8%** | 70.1% |
| datasources | 31 | 13.8% | 38.7% | 38.7% |
| other | 90 | 85.2% | 66.7% | **77.8%** |
| **总通过** | 1732 | 68.1% | **89.4%** | **87.3%** |

**差距几乎全部来自 schema 一块**：v1.4.6 做到 94.9%，本版只有 86.0%。
migrate、basic/cli 基本持平，other 反而明显更好（66.7% → 77.8%）。

## 3.2 修复归因：修好了 52 个，退掉了 87 个

拿本版与 v1.4.6 逐测试比对：

| | 数量 |
|---|---|
| v1.4.6 失败 → v1.5.1 通过 | **52** |
| v1.4.6 通过 → v1.5.1 失败 | **87** |
| 净变化 | **−35** |

修复的样例：
```
test_schema_diff_include_flag                    ← 社区版 gated flag
test_migrate_apply_workflow                      ← migrate 执行链路
test_multiple_schema_sources                     ← 多 schema 源
test_unsupported_migrate_checkpoint_with_abort_prefix  ← 隐藏命令
test_ent_revision_create                         ← ent 迁移表
```

回退的样例：
```
test_positional_invalid_integer                  ← migrate apply 参数校验
test_double_dash_treats_following_as_positional   ← 参数解析
test_flag_repeat_last_wins_for_env               ← flag 重复语义
test_help_for_nonexistent_command                ← help 边界
test_invalid_hcl_syntax_error                    ← HCL 报错
```

**回退集中在 schema 和参数解析**——正是本版改动最大、检查最密的地方。

## 3.3 为什么检查多了反而退步

结合功能块数据，原因是**检查的分布不均衡**：

| 模块 | checks 数 | 效果 |
|---|---|---|
| schema_inspect | 56 | 会话跑满 170+ 步仍未收敛 |
| schema_apply | 13 | 正常 |
| migrate_apply | 6 | 相对不足 |

一个模块被塞进 56 条检查，会话预算（150 步）根本不够，结果是一部分检查过了、
另一部分没做完，同时把 v1.4.6 原本能过的行为挤掉了。

**检查数量不是均匀有益的：它把模块会话的注意力从"整体行为"拉向"逐条对断言"，
而评测测的是整体行为。**

## 3.4 成本与时长：为什么省了钱却更慢

| | v1.4.6 | **v1.5.1** |
|---|---|---|
| 总成本 | $64.9 | **$39.0** |
| API 调用 | 1442 | 1164 |
| 输入 token | 188.9M | 129.2M |
| 输出 token | 1.78M | 1.38M |
| 缓存命中 | 97.5% | 98.2% |
| 每次调用成本 | $0.0411 | **$0.0335** |
| 墙钟时长 | 4.6h | **8.4h** |

成本和时长往相反方向走，把轨迹按阶段拆开就清楚了。

| 阶段 | v1.4.6 耗时 | v1.5.1 耗时 | 调用次数 |
|---|---|---|---|
| probe | 27 min | **76 min** | 128 → 200 |
| plan | 26 min | 34 min | 39 → 84 |
| implement（10 个模块串行合计） | **8.6 h** | 5.9 h | 1220 → 713 |
| integrate | 32 min | 36 min | 190 → 167 |

**钱省在 implement。** 调用次数从 1442 降到 1164，其中 implement 少调了 507 次。
给了断言之后，模块会话知道自己该改到哪为止，不用反复读大段输出试错。单次调用也便宜
了 18%——平均输入从 120K token 降到 111K，上下文没撑那么大。

**时间花在 probe。** 探测从 27 分钟变成 76 分钟：断言要做到 198 条，探测 agent 得把
每条子命令、每种输入族、每个 gated 命令都真跑一遍。这 50 分钟是纯墙钟时间，但几乎不
花钱——探测跑在便宜模型上，全程只用了 $0.38。

**墙钟翻倍的主因是模块没并发，不是 token。** 两轮的实现阶段设置了不同的并发度：

| | 模块串行合计 | 实际时间跨度 | 并发 |
|---|---|---|---|
| v1.4.6 | 8.6 h | **3.2 h** | 多模块并发（9 个分三波启动） |
| v1.5.1 | 5.9 h | **5.9 h** | `--workers 1`，10 个模块首尾相接 |

轨迹里的时间戳能直接看出来：v1.4.6 的模块在 21:37 同时起跑，v1.5.1 是
02:21→02:36→03:13→…→08:17 一个接一个，没有任何重叠。

单看每个模块 v1.5.1 其实更快（合计 5.9 小时对 8.6 小时），但因为串行执行，墙钟反而
更长。这不是代码差异——线程池一直存在（`--workers` 同时控制实例和模块两级的并发度），
是这轮启动时给了 1。按 `change_log.md` 的记录，前几版用 workers 8 让模块一波跑完，
墙钟能压到 2 小时左右。

一句话：**省下的钱来自更少的无效试探，多花的时间来自更彻底的探测。**

## 3.5 与历史版本的方差对比

| 版本 | 各次分数 | 极差 |
|---|---|---|
| v1.4.8（三次） | 78 / 79 / 77 | 2 |
| v1.5（四次，DeepSeek） | 70 / 76 / 69 / 74 | 7 |

本版只保留了最好的那次运行（另有一次 84.8 分，因差异来自采样波动未保留）。
v1.4.8 与本版同为 GLM，极差 2 分，说明「断言无上限」这个改动本身是稳定的。

# 四、结论

1. **断言的真实性第一次被程序把关**：上一版的 56 条断言没有任何一条被验证过，模型
   说验证了就当成验证了。本版把验证做成程序实跑，立刻发现探测写出的 198 条里有 57 条
   是错的——三分之一的断言不成立。

2. **验证器自己也会误判，而且更隐蔽**：同一批断言，换一种验证实现，有效数从 118 变
   成 254。断言是被验证环境判死的，不是被真实行为判死的。修复三处路径缺陷后，淘汰从
   149 条降到 3 条。

3. **可信的断言变多了，但分配没跟上**：断言从 56 条提到 137 条，`schema` 一块反而
   从 94.9% 掉到 86.0%，因为 `schema_inspect` 一个模块塞了 56 条，150 步预算下无法
   收敛，挤掉了原本能过的行为。净结果是修好 52 个、退掉 87 个。

4. **下一版的靶子是断言的分配，不是断言的数量**：需要让每个模块的断言数和它的会话
   预算匹配，断言过载的模块应当拆开；同时 `schema` 域的回退要逐条追。

   v1.4.6 用 56 条断言拿到 89 分，本版用 137 条拿到 87 分——**断言数量与分数之间
   不是单调关系，分布才是关键。**
