# 一、优化动机

## 1.1 上一版的失败集中在深层行为

v1.4.6 的上一版拿到 84 分，还有 310 个测试没过，而且失败扎堆在一类命令的深层行为上。
当时的判断是"探测没覆盖到"，但把失败的每一类行为拿去比对探测记录，发现不是这么回事：

| 行为类型 | 探测阶段有没有记录到 | 测试结果 |
|---|---|---|
| baseline、tx-mode、exec-order、allow-dirty、exclude | **记录到了，还记录了正确输出** | **仍然失败** |
| template、index、foreign key、unique | 没记录到 | 失败 |

九类失败行为里，有五类早就探测到了，甚至连它们成功时的正确输出都记下来了，可测试
还是没过。

## 1.2 原因：探到的真相没被拿来核对实现

探测阶段的产物 `probe_findings.json` 每条只有四个字段：命令、标准输出、标准错误、
退出码。它忠实记录了程序对终端说了什么，但有两个局限：

- **记录不了副作用**。比如 `migrate new` 创建了两个文件，标准输出是空的、退出码是 0，
  "创建了文件"这件事在四个字段里完全看不出来。
- **记录不了前置条件**。它只记了"我跑的时候看到了什么"，没记"跑之前环境长什么样"，
  别人拿到这条记录也复现不出来。

更关键的是，这些记录只是被写成一段文字交给写代码的 agent，agent 理解了、照着写，
最后自己觉得写对了就交差，从头到尾没有人拿真实输出核对过它写的东西到底对不对。

> 探测到的真相停留在"参考资料"层面，从未被用来"卡"实现。

这就是这一版要解决的动机：**把探测到的正确输出，从"给 agent 参考的文字"变成
"必须逐条通过的检查"。**

# 二、v1.4.6 版本改动

本次只新增一件事：checks 检查机制。没有增加流水线阶段，只是在探测、规划、实现三个
阶段各加了一步。

## 2.1 整体思路

```
探测阶段          规划阶段            实现阶段           集成阶段
probe            plan               implement          integrate
   │                │                  │                  │
整理出可运行的      把这些检查逐条       写完代码要跑通      照旧做全局修复
行为检查清单        分配给对应模块       本模块的检查
```

checks 在各阶段的位置：

| 阶段 | 对 checks 做什么 | 说明 |
|---|---|---|
| probe | **生成** | 探测 agent 在跑黑盒的同时，把重要行为提炼成检查 |
| plan | **读取并分派** | 把每条检查挂到负责该命令的模块的契约里 |
| **implement** | **执行** | **唯一真正跑 checks 的阶段**，模块收尾时必须全绿 |
| integrate | 未使用 | 原计划让集成收尾也全跑一遍，本次未实现 |
| 评测 | 无关 | 评分用的是官方隐藏测试，与 checks 无关 |

## 2.2 三个阶段各加了什么

| 阶段 | 改动 |
|---|---|
| **probe** | 除 `probe_findings.json` 外，额外产出 `probe_checks.json`：把真实观测固化成可执行断言 `{command, setup, expect{exit_code/stdout_contains/stdout_regex/stderr_*/files_exist}}` |
| **plan** | 读 checks 并**逐条分派到模块**，写进 contracts.json 每模块 `checks` 字段，不增不减 |
| **implement** | 收尾**跑本模块 checks**，全绿才收工；**有界修复**最多两轮；checks 结果写进 module_status.md |

**关键设计决策**：

- **易变字段必须用模式匹配**：一个因时间戳变化而失败的 check 比没有 check 更糟
- **有界修复**：防止 checks 变成新的"无限打磨"陷阱，v1.1 踩过这个坑
- **每条检查自带前置状态**：建库、写文件都写在 setup 里，保证从干净环境能复现

## 2.3 实际验证

| 环节 | 结果 |
|---|---|
| probe 产出 checks | **56 条**，格式全合规，44 条带 setup 前置状态 |
| plan 分派 | **56/56 全分派**到 9 模块，`migrate_apply` 拿到最多的 12 条 |
| implement 跑 checks | 收尾验收生效，模块普遍一路修到步数用满 |

一条真实的检查长这样：

```json
{ "command": "./executable migrate import --from 'file://.../src?format=golang-migrate' --to file://.../dst",
  "setup": "rm -rf .../imp && mkdir -p .../src .../dst && printf 'CREATE TABLE `a`...' > .../0001_a.up.sql ...",
  "expect": { "exit_code": 0, "files_exist": [".../dst/atlas.sum", ".../dst/0001_a.sql"] } }
```

它断言的是副作用：导入后目标目录真的生成了迁移文件，而不是易变的终端输出。

## 2.4 checks 的字段说明

顶层三个字段：

| 字段 | 含义 |
|---|---|
| `command` | 要运行的命令 |
| `setup` | 运行前要执行的准备命令，没有则为 null |
| `expect` | 运行后要核对的内容，详见下表 |

`expect` 的六个可选字段，每条检查按需选用：

| 字段 | 断言什么 | 典型用途 |
|---|---|---|
| `exit_code` | 退出码完全等于给定值 | 唯一一条每条检查必有的字段 |
| `stdout_contains` | 标准输出包含给定子串 | 稳定文字，如 `Migrating to version` |
| `stderr_contains` | 标准错误包含给定子串 | 报错文字，如 `required flag` |
| `stdout_regex` | 标准输出匹配正则 | 会变的内容，如时间戳、版本号 |
| `stderr_regex` | 标准错误匹配正则 | 报错中的可变部分 |
| `files_exist` | 运行后这些文件必须存在 | 副作用，如 `atlas.sum` |

字段不固定是刻意为之：只断言那条命令真正可观察、而且稳定的部分。实际分布是
`exit_code` 56 条全部具备，`stdout_contains` 26 条，`stderr_contains` 21 条，
`stdout_regex` 6 条，`files_exist` 6 条，`stderr_regex` 1 条；每条检查大多只带
两到三个字段。

## 2.5 checks 是怎么来的、怎么分模块的

### 生成方式

checks 由探测 agent 自己写，不是程序自动从 findings 抽取的。过程是：agent 探测时
跑过某条命令、看到真实结果，然后挑出重要行为，照着看到的结果反写成一条检查：
`setup` 照抄当时准备环境的命令，`expect` 摘出输出里稳定的部分，写进
`probe_checks.json`。

### 分模块

容易误解的一点：plan 阶段并非把 findings 和 checks 两份都分发下去。

- **findings 不分模块**，它只作为 plan 设计"该切成哪几个模块"的依据
- **只有 checks 被分模块**：plan 看每条检查跑的是什么命令，判断哪个模块拥有这条
  命令，就挂到那个模块的契约里

本次实际分派：`migrate_apply` 12 条，`schema_apply`、`schema_diff`、`migrate_dir`
各 7 条，`root`、`schema_inspect` 各 6 条，`project` 5 条，`schema_fmt`、
`migrate_diff` 各 3 条，合计 56 条。

## 2.6 已知短板

**短板一：检查本身可能写错。** 提示词要求只收录验证跑通过的检查，但产物里无法确认
agent 真的逐条重跑验证过，更可能是根据已有结果反推。反推就可能出笔误，比如 setup
建的目录和 command 里写的路径对不上。`migrate_apply` 分到 12 条检查、最终修满 150
步仍未收敛，不排除部分检查本身有问题。

**短板二：检查可能太弱。** 有 2 条检查只有 `exit_code` 一个字段，只要实现能让命令
正常退出就算过，输出对不对完全不管，挡不住错误实现。

**短板三：分模块没有校验。** checks 和 findings 之间没有显式关联字段，同一模块是靠
命令归属间接推出来的。检查可能挂错模块，跨模块的命令只能挂给一个模块，也可能被遗漏。
目前唯一的保护是 implement 前打印一行计数"探测 56 条、分配 56 条"，只打印不拦截。

**短板四：覆盖率有限。** 146 条 findings 只提炼出 56 条 checks。剩下约六成的行为，
implement 阶段仍然只靠契约文字描述，没有可执行验收。这也是这一版停在 89 分而不是
更高的原因之一：checks 覆盖到的地方修好了，没覆盖到的地方还是老样子。

**改进方向**：三处靠 agent 自觉的地方都可以用程序兜底取代，一是程序把每条检查实际
跑一遍，跑不出预期结果就退回重写；二是拒绝只有 exit_code 的过弱检查；三是核对每条
检查有且只有一个归属。至于覆盖率，可以考虑对输出全是易变内容的命令断言结构而非值，
对文件产物断言内容模式而非仅存在性。以上本次均未实现。

**migrate、schema 是主拉力**——正是 checks 覆盖最密的两个域。

## 3.2 修复归因：checks 精准命中了深层语义

**净修复 169 个测试，仅回退 40 个**（净 +129）。修复的测试样例：

```
test_apply_template_lower_function_undefined      ← Go template 渲染（此前整片挂）
test_schema_inspect_template_json_format          ← template 输出格式
test_schema_inspect_template_mermaid_format
test_schema_apply_missing_to_flag                 ← 参数校验
test_schema_apply_requires_to_or_file_when_url_set
test_schema_fmt_directory_only_formats_hcl_files  ← fmt 目录行为
test_status_template_empty_array_conditional      ← status template 边界
```

**全部是"需要成功执行才能观测"的行为**——正是 checks 机制的靶心，也反过来
印证了第一节的归因：不是探不到，是**没把探到的真相用于验收**。

## 3.3 副作用观察

- **多数模块 `LimitsExceeded`（用满 150 步）**，此前版本多为 `Submitted`。这是
  **预期**：checks 给了客观完成标准，agent 会一直修到预算耗尽。修出了 169 个
  测试，不是浪费——但成本相应偏高、没有余量。
- **40 个回退**：需在下一版关注（可能是 checks 未覆盖的角落被挤占，或易变字段
  处理不当导致的假通过）。
- integrate 自然提交（190 步，未撞 300 上限）。

## 3.4 成本

生成总成本 **$64.9**。成本结构：模块普遍用满 150 步（9 模块合计 ~$57）+
integrate $6.1 + plan $1.3 + probe $0.14。**probe 只花 $0.14 却产出了 56 条
验收断言**——这是整条链里最高杠杆的一环。

# 四、结论

1. **checks 验收机制有效**：89 分（系列新高），净修复 169 个测试
2. **归因的方法论价值**：5/9 失败族的 probe 证据齐全但测试仍挂，证明瓶颈在
   "探到的真相没用于验收"而非"采集不足"——这个纠错避免了我们继续在 probe
   提示词上做无效投入
3. **修复精准命中深层语义**：template 渲染、参数校验、目录行为——
   全是"成功执行才能观测"的行为，正是 checks 的靶心
4. **验收的判定从模型交给机器**：这是 v1.4.6 全部价值的来源——模型自评不可靠，
   可执行断言可靠
5. **代价与遗留**：模块普遍用满步数（成本无余量），40 个回退待分析；checks 的生成、
   强度和分派依赖 agent 自觉而没有程序兜底，覆盖率也有限，详见 2.6，是下一版最该补的地方
