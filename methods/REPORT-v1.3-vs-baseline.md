# 递归生成 harness（v1.3）vs 官方 baseline 对比报告

**任务**：`ariga__atlas.6d81150`（Atlas 数据库 schema 管理 CLI，Go）

| | baseline | v1.3 | 差异 |
|---|---|---|---|
| **分数** | 72 | **83** | **+11** |
| **成本** | $36.46 | $41.53 | +14% |
| **时长** | 2.6h | 3.0h | +15% |
| **每分成本** | $0.51 | $0.50 | 效率持平 |

---

# 一、Harness 框架概括

## 1.1 baseline：单会话一次成型

官方 harness 把整个逆向工程任务交给**一个 agent 会话**：

```
系统提示（500 行级：你是逆向工程师，写出完整代码库）
    ↓ 单个会话，最多 1000 步
模型自主决定：探测 → 写码 → 自测 → 修错 …（全部在同一上下文里）
    ↓ 上下文一路膨胀（实测最大 53 万 token）
产出 /workspace → 打包 submission.tar.gz
```

**特点**：模型自由度高、无阶段约束；上下文随步数线性膨胀；单一会话承担所有职责。

## 1.2 v1.3：四阶段流水线 + 契约驱动

把任务拆成 **4 个独立 agent 会话的阶段**，上下文只通过**结构化产物**传递：

```
┌─ probe ────┐  ┌─ plan ─────┐  ┌─ implement ─┐  ┌─ integrate ─┐
│ 探测黑盒    │→ │ 架构设计    │→ │ 并行实现     │→ │ 集成修复     │
│ Flash 模型  │  │ 5.3 模型    │  │ 5.3, N 并行  │  │ 5.3 模型     │
│            │  │            │  │             │  │             │
│ 脚本枚举    │  │ 冻结契约    │  │ 每模块独立   │  │ 全局优先级   │
│ + LLM 补盲  │  │ + 骨架      │  │ 会话+回归    │  │ 修复         │
└────────────┘  └────────────┘  └─────────────┘  └─────────────┘
   probe_          contracts.json   各模块代码         submission
   findings.json   + compile.sh     + 状态文件
```

**四条核心设计**：

| 设计 | 内容 | 解决的问题 |
|---|---|---|
| **契约冻结** | plan 产出 `contracts.json`，定义每个模块的接口；后续阶段不许私改 | 模块间零越界，防屎山 |
| **上下文隔离** | 每模块一个独立会话，只看得见自己的契约（几万 token，不膨胀） | 避免 53 万 token 的上下文稀释 |
| **修复职责后移** | 模块最多修 2 轮就停 + 写 `module_status.md`；integrate 读状态做全局优先级修复 | 消除「模块盲目打磨」（v1.1 时长 10.4h 的根因） |
| **构建前置** | `compile.sh` 在 plan 阶段就写好并验证可离线构建 | 消除 compile_failed 归零风险 |

**模型分工**：probe 用 GLM-5.3-Flash（1/20 价格，探测是机械活），其余用 GLM-5.3。

# 二、结果对比：分功能块

**总测试数 1732**（有效 1318）。按 atlas 的功能域聚合成 7 块：

| 功能块 | 测试数 | baseline | v1.3 | 变化 |
|---|---|---|---|---|
| **basic/cli** | 719 | 707 (98.3%) | 713 (**99.2%**) | +1pp |
| **migrate** | 451 | 175 (38.8%) | 301 (**66.7%**) | **+28pp** |
| **schema** | 278 | 188 (67.6%) | 196 (**70.5%**) | +3pp |
| **cmdlog** | 86 | 4 (4.7%) | 46 (**53.5%**) | **+49pp** |
| **config/env** | 77 | 55 (71.4%) | 62 (**80.5%**) | +9pp |
| **datasources** | 31 | 0 (0.0%) | 8 (**25.8%**) | **+26pp** |
| other | 90 | 51 (56.7%) | 59 (65.6%) | +9pp |
| **总计** | **1732** | **1180 (68.1%)** | **1385 (80.0%)** | **+12pp** |

## 关键观察

1. **全部 7 块都提升**，没有一块退步
2. **长尾块提升最猛**——正是 baseline 拿不到分的部分：
   - `cmdlog`：4.7% → 53.5%（**11 倍**）
   - `migrate`：38.8% → 66.7%
   - `datasources`：0% → 25.8%（**从零到有**）
3. **基础块已接近饱和**（basic/cli 99.2%），提升空间在长尾

## 各块是什么

| 块 | 对应 atlas 功能 |
|---|---|
| basic/cli | `--help`、version、命令补全、参数解析、错误提示 |
| migrate | `atlas migrate new/apply/status/diff/validate` 版本化迁移管理 |
| schema | `atlas schema inspect/diff/apply/fmt` 声明式 schema 管理 |
| cmdlog | 命令输出格式（模板渲染、条件输出、颜色） |
| config/env | `atlas.hcl` 配置解析、`--env` 多环境 |
| datasources | 数据源连接：URL scheme 解析、HCL `data` 块、云 token |

# 三、效果归因

## 3.1 为什么 v1.3 能反超 baseline 11 分

### 归因 1：长尾功能被系统覆盖（贡献最大）

**baseline 的失败模式**：单会话里，模型把预算花在它「看得见」的功能上（help、基础命令），
**README 里没写清楚的功能就漏掉了**。实测 baseline 的 cmdlog 只有 4.7%、datasources 0%。

**v1.3 的机制**：probe 阶段**系统枚举**（脚本遍历 help 树 + LLM 补盲区 + HCL data 块类型枚举），
把「有哪些功能」变成一份**显式清单**（probe_findings.json），再交给 plan 分配成模块契约。
模型不再依赖「自己想到」，而是**按清单施工**。

**证据**：datasources 从 0% → 25.8% 完全来自 probe 的 data 块枚举（v1.2 没枚举时是 0%）。

### 归因 2：每个功能块获得足够的专注预算

**baseline 的问题**：单会话上下文里，53 万 token 的历史让模型「什么都看到一点，什么都做不深」。
后期注意力稀释，migrate 这种复杂功能被浅实现。

**v1.3 的机制**：每模块一个独立会话，上下文只有几万 token，**全部注意力在本模块**。
模块可以对着黑盒反复对拍、把边角行为做对。

**证据**：migrate 38.8% → 66.7%，cmdlog 4.7% → 53.5%——都是需要「深挖边角」的块。

### 归因 3：修复发生在有全局视角的地方

**v1.1 的教训**：模块自己死磕到「回归全绿」（10.4h），但模块看不到全局，
把预算花在测试根本不考的边角上。

**v1.3 的机制**：模块只修 2 轮就停 + 交出 `module_status.md`（精确记录哪些失败）；
integrate 汇总所有模块的状态，**按影响面排序修复**——这才是「知道什么值得修」的地方。

**证据**：v1.1 时长 10.4h → v1.3 3.0h（**降 71%**），分数反而 80 → 83。

### 归因 4：构建风险前置消除

**baseline 无此问题**（单会话自然包含构建），但 v1 版本曾因 compile.sh 没写出来而 **0 分**。
v1.3 把 compile.sh 放进 plan 骨架并验证，integrate 只调代码不重写——**消除归零风险**。

## 3.2 成本归因：为什么只贵 14%

| 阶段 | v1.3 成本 | 说明 |
|---|---|---|
| probe | $0.13 | Flash 模型，占 0.3% |
| plan | $5.61 | 契约 + 骨架 + compile.sh |
| implement ×10 | $26.03 | 主力模型，每模块 ~$2.6 |
| integrate | $9.76 | 全局修复 |

**相比 baseline 只贵 $5**，但换来：
- 多 1.9 倍 API 调用（1180 vs 381）
- 输出 token 3 倍（1228K vs 409K）——更多代码和对拍
- 输入 token 基本持平（118M vs 108M）——**因为上下文不膨胀**（每模块独立 vs baseline 单会话膨胀到 53 万）

**这是关键效率点**：v1.3 用「多会话小上下文」替代「单会话大上下文」，
在输入 token 几乎不变的前提下，让模型做了 3 倍的输出工作。

## 3.3 时长归因：为什么只慢 15%

- 阶段串行（probe→plan→implement→integrate）+ 每会话冷启动
- 但模块并行（workers=5）+ 修复预算（模块不无限打磨）抵消了大部分开销
- **环境因素**：跑的那天所里网关不稳定，有多次 504 重试（非框架问题）

# 四、v1.3 的局限与已知问题

| 问题 | 现状 | 影响 |
|---|---|---|
| **模块划分随机性** | 同一 prompt，plan 每次分出 9-10 个不同模块 | 80-83 分波动的主因 |
| datasources 仅 26% | 只覆盖了 data 块的错误路径 | 云集成行为需要真实环境，难探测 |
| 依赖网关稳定性 | 网关挂死会拖慢/中断 | 已加 timeout + 断点续跑兜底 |
| 成本仍高于 baseline | $41.5 vs $36.5 | 但分数 +11，效率持平 |

---

# 五、结论

1. **v1.3 全面优于 baseline**：分数 +11（72→83），7 个功能块全部提升，成本仅 +14%
2. **提升来自机制而非堆预算**：长尾块（cmdlog +49pp、migrate +28pp、datasources +26pp）的
   提升源于「系统探测 → 契约分配 → 专注实现 → 全局修复」的流水线设计
3. **最大剩余瓶颈是模块划分的随机性**（80-83 波动）——下一步应让 plan 按固定功能清单划分
4. **方法论意义**：证明了「把单体 agent 任务拆成契约驱动的多阶段流水线」在逆向工程场景有效，
   且成本可控
